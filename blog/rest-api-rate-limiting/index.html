Versioning and deprecation

The right pattern is rarely the clever one. The right pattern is the boring one, instrumented, with a runbook. This section is about making the boring one work.

Idempotency is the contract

A retry is not an error condition; it is a normal operation. The API that is not idempotent cannot be retried safely.

Security: auth, authz, rate limiting

The performance of api in api is rarely the bottleneck. The bottleneck is the missing index, the unindexed join, the report that fetches every row and filters in the layout.

Rate limiting is a contract

A rate limit that is not enforced is a suggestion. A rate limit that is enforced is a contract. The contract is what the client can rely on.

PatternWhen to use it
Boring api firstSimple, observable, easy to roll back. Use this for the first version of anything.
Add rest on topOnce the boring version is in production, layer the framework on top. Do not skip the boring version.
Replace with api when measuredWhen the data tells you the boring version is too slow, replace. Measure before and after.
Document the trade-offEvery pattern has a trade-off. Document it. The next person will read the doc.
