Acumatica REST API — Pagination and OData

How to paginate through large Acumatica REST result sets using $top, $skip, and continuation tokens — plus a guide to the OData query options that actually work in Acumatica.

John KihiuMay 22, 202612 min read

Acumatica's contract-based REST API supports a standard set of OData-style query string parameters — $top, $skip, $filter, $expand, $select, and $custom — against every endpoint under /entity/{endpointName}/{version}/. Most of the integration bugs I get called in to fix aren't about getting data out of Acumatica; they're about pulling it out efficiently, in order, without falling over on a 200,000-row Sales Order export. This post covers how pagination actually behaves, which OData options are worth using, and where the pattern breaks down at scale.

Basic $top / $skip pagination

The REST API doesn't return a total record count or a next-page cursor by default. The standard pattern is to fix a page size with $top and increment $skip by that same amount on each subsequent call, continuing until a response comes back with fewer records than you asked for — that's your signal you've hit the last page.

There's no server-side "hasMore" flag or continuation token in the base contract API, so client code has to track this itself. A typical loop keeps a running offset, requests $top=100 each time, and stops as soon as the returned array length is less than 100.

Filtering with $filter

OData filter expressions let you narrow results server-side instead of pulling everything and filtering in your client. Acumatica supports the usual operators — eq, ne, gt, ge, lt, le, combined with and / or — against fields exposed in the endpoint contract. Filtering on an indexed field like OrderNbr, Status, or a date field is far cheaper than fetching unfiltered pages and discarding rows client-side.

This matters more than it sounds: every unnecessary row Acumatica has to serialize and you have to deserialize is time your integration is holding open a session against a production app pool.

Controlling payload with $select and $expand

By default a GET against an endpoint like SalesOrder returns the full contract shape for the header, but not the detail lines — for those you need $expand=Details. That's convenient for a single-record lookup, but expanding details across a bulk paginated pull multiplies payload size fast: 100 orders with 20 lines each is 2,000 detail rows serialized into one response.

Use $select to trim the field list down to what the downstream system actually consumes. Combining a tight $select with $expand only on the detail entities you need keeps response times predictable as page count grows. Pulling every field on every entity "just in case" is the single most common cause of slow syncs I see in the field.

Deep $skip gets expensive

Acumatica translates $top/$skip into an OFFSET/FETCH query against the underlying SQL Server tables. As $skip grows into the tens of thousands, the database still has to walk and discard every prior row before it can return your page — response times degrade the further into a dataset you page. For large historical exports, filter on a monotonic field instead of paging deep.

Incremental sync instead of deep paging

For anything beyond a few thousand records, I avoid deep $skip entirely. Acumatica exposes LastModifiedDateTime on most entities, so the more reliable pattern is a keyset-style sync: filter with LastModifiedDateTime gt {last synced timestamp}, order ascending, and page through only the delta since the last run. This avoids the offset cost altogether and gives you incremental sync for free — you only ever request records that changed, not the whole table on every run.

Record the highest LastModifiedDateTime you've seen at the end of each run and use it as the filter floor next time. It's a small amount of state to track compared to re-running a full paginated export on every sync.

Authentication and session context

Paginated pulls need to reuse the same authenticated context across every page — either a cookie-based session from /entity/auth/login or an OAuth 2.0 bearer token. Some query state in Acumatica is tied to the session, so rotating credentials mid-pagination or spreading pages across parallel sessions can produce inconsistent results. Keep one session (or token) alive for the duration of a paginated export, and log out cleanly when you're done rather than letting sessions pile up.

Acumatica doesn't publish a fixed public rate limit the way some SaaS APIs do, but a long-running paginated pull competes with real UI users for the same application pool worker threads. On a production instance, that means a bulk sync during business hours can visibly slow the screen for whoever's entering Sales Orders at the same time. Run large exports off-peak, or through a dedicated integration user with its own throttling, rather than firing pages as fast as the client can go.

GET /entity/Default/24.200.001/SalesOrder
    ?$filter=LastModifiedDateTime gt datetimeoffset'2026-07-01T00:00:00Z'
      and Status eq 'Open'
    &$select=OrderNbr,OrderType,Status,CustomerID,OrderTotal,LastModifiedDateTime
    &$expand=Details
    &$top=100
    &$skip=0
Cookie: ASP.NET_SessionId=<session-from-auth-login>
Accept: application/json
ParameterPurpose
$topPage size — number of records to return per call.
$skipOffset — number of records to skip before returning results.
$filterServer-side filtering with eq, gt, and, or, etc. against contract fields.
$expandInclude related detail entities (e.g. line items) in the same response.
$selectLimit returned fields to reduce payload size and serialization cost.
$customRequest custom or Usr- fields not present in the default contract.
