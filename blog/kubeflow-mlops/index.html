The CI/CD pipeline integration

The right pattern is rarely the clever one. The right pattern is the boring one, instrumented, with a runbook. This section is about making the boring one work.

The on-call is the test

A DevOps practice that survives a bad on-call rotation is a good practice. A practice that breaks under the on-call is broken.

Observability: metrics, logs, traces

I have shipped this pattern a few times. The first time it took a week. The second time it took a day. The third time it took an hour. The pattern is to start with the boring version and replace as needed.

Security: secrets, RBAC, network policies

The performance of mlops in devops is rarely the bottleneck. The bottleneck is the missing index, the unindexed join, the report that fetches every row and filters in the layout.

Logs are the last resort

If you are reading logs to debug, your metrics and traces are not good enough. The right signal is a metric or a trace; logs are for the deep-dive when neither helps.

Cost optimisation

PatternWhen to use it
Boring mlops firstSimple, observable, easy to roll back. Use this for the first version of anything.
Add kubeflow on topOnce the boring version is in production, layer the framework on top. Do not skip the boring version.
Replace with mlops when measuredWhen the data tells you the boring version is too slow, replace. Measure before and after.
Document the trade-offEvery pattern has a trade-off. Document it. The next person will read the doc.
