Acumatica Rebuild and Publish Best Practices

The build-publish-validate cycle for Acumatica customizations — when to rebuild, when to publish, when to validate, and the order of operations that prevents the

John KihiuApr 30, 202612 min read

Every Acumatica customization project sits on a small state machine: edit, compile, publish, verify. Teams that skip steps or get the order wrong end up with a site stuck "compiling" during business hours, a generic inquiry that silently vanished, or two projects that overwrite each other's DAC extension. None of that is exotic — it's almost always a sequencing mistake that a checklist would have caught.

Compile vs. publish vs. rebuild

These three actions in the Customization Projects screen look similar but do very different things. Compile only validates that the project's code, DAC extensions, and graph extensions build cleanly — it does not touch the running site. Use it constantly while developing; it's cheap and safe to run against a live instance because nothing gets replaced.

Publish compiles and then deploys — it replaces the site's running assemblies, updates the database schema for any DAC changes, regenerates the site map, and triggers an application pool recycle. Every user gets bounced and the site is unavailable for the duration. Rebuild (via "Rebuild All" or "Clear Cache and Rebuild") forces a full recompilation of the customization runtime rather than an incremental one — it's a troubleshooting step, not something you run as part of a normal release, because it's slower and clears cached generic inquiry and screen metadata across the board.

Publish order and project dependencies

Acumatica lets you select multiple customization projects and publish them together, and in most cases that's the safer option — the platform resolves dependencies between the selected projects in a single compile pass. The trouble starts when projects are published separately and one depends on another: a project that extends a DAC field added by a different project will fail to compile if that base project isn't published first (or alongside it). If you maintain a suite of projects — say a core "Data Model" project and several feature projects layered on top — publish them as one selection whenever possible rather than clicking through them one at a time.

Two projects modifying the same table are the other common failure. If Project A adds a column to a DAC and Project B independently adds a same-named field or an incompatible index on the same table, publish will throw a schema conflict. Keep a single project (or a clearly owned subset) responsible for shared DAC changes, and have feature projects extend it rather than duplicate it.

What goes wrong during publish

On constrained cloud or trial instances, publish can time out on large codebases — the app pool recycle takes longer than the request timeout and the browser reports a failure even though the publish is still finishing server-side. Don't panic-click publish again; check the trace log first. A failed or interrupted publish can also leave orphaned entries: generic inquiries or site map nodes that were partially created before the rollback, which then show up as broken links or duplicate menu items until cleaned up manually.

The other common symptom is the site sitting in an unresponsive or "compiling" state for anyone hitting it during the publish window. There's no partial availability — end users need to be warned or locked out, which is why publishing to production mid-morning on a Tuesday is asking for a support ticket.

Never publish blind to production

Publish to a sandbox or test tenant first — ideally one restored from a recent production snapshot — and let it sit long enough to catch startup errors in the trace log and Windows Event Viewer. A clean compile in isolated storage does not guarantee a clean publish against production's actual data and existing customizations.

Promotion pipeline: dev to test to production

Treat the customization project like a build artifact, not a live-edited document. Export the finished project as a .zip package from the dev environment, import it into the test tenant, publish there, and only promote the same .zip to production once it's verified — rather than re-creating the changes by hand in each environment. This keeps the three environments byte-identical and makes rollback trivial: if production publish fails, you still have the last-known-good .zip to re-import.

POWERSHELL · EXPORT/IMPORT VIA CUSTOMIZATION CLI
# Export from dev after a clean local publish
CustomizationCli.exe export `
  -url https://dev.example.com `
  -project "CoreDataModel;ARInvoiceExtensions" `
  -output C:\releases\core-2026-04-30.zip

# Import + publish into the test tenant, dependencies resolved together
CustomizationCli.exe import `
  -url https://test.example.com `
  -file C:\releases\core-2026-04-30.zip `
  -publish

# Same package promoted to production after sign-off, outside business hours
CustomizationCli.exe import `
  -url https://prod.example.com `
  -file C:\releases\core-2026-04-30.zip `
  -publish

Before that last step: take a database backup or system snapshot, export the currently-live customization project as a fallback, and schedule the window outside business hours. After publish completes, watch the trace log for a few minutes — startup exceptions from a bad DAC extension or a missing dependency usually surface in the first requests, not immediately at publish completion.
